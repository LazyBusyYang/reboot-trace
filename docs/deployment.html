部署设计

后端作为普通进程直接运行在每个目标容器内；前端镜像可独立聚合多个后端。

首页需求架构数据库接口前端部署

1. 交付物

backend/Dockerfile
frontend/Dockerfile
deploy/compose.example.yaml
deploy/runtime-config.example.json

后端 Dockerfile 仅用于构建和依赖门禁，不能作为兄弟容器观测目标 Kubernetes 容器，也不承诺使用默认配置即可运行。生产后端必须把同一套 Python 包作为非 root 原生进程装入目标容器；项目不把 SQLite 文件烘焙进镜像。

2. 后端原生进程要求

  • 后端与目标 PID 1 必须处于相同 PID 和 mount namespace，并直接读取本地 /proc；启动后通过状态接口核验同源结果。
  • 数据默认建议放在 <项目根>/var/reboot-trace，活动库、只读生命周期胶囊、manifest、quarantine、host-id 和迁移状态均位于该目录；该目录已被 Git 忽略。
  • Git 项目目录并非必须部署在持久挂载上。运维人员必须检查实际数据路径：若项目目录不持久，应将 RT_DATA_DIR 指向另一个经真实重建验证的持久挂载。
  • 监听 0.0.0.0:8080；健康检查访问 /health/ready。
  • 后端进程停止时优雅关闭并记录 collector_stopped；采集服务停止本身不得终结目标容器生命周期。
  • 应用进程使用固定非 root UID/GID 10001；只需赋予数据目录与 /run/reboot-trace 的窄范围写权限。

2.1 容器实例标记

标准部署在启动前创建权限 0700、由后端 UID 所有的 /run/reboot-trace。无法使用 root 准备目录的 dev1/4/5/9 通过实例脚本使用 /tmp/reboot-trace-${UID}/container-instance-id；这只在 PID 1 mountinfo 将该路径解析为根 overlay/fuse-overlayfs 时受支持。不得把 marker 目录挂载为 volume、hostPath、PVC、emptyDir 或单独 tmpfs。后端进程重启时 marker 保留，干净重建容器时 marker 消失。通用部署在无法证明时降级；设置 RT_REQUIRE_CONTAINER_MARKER=true 会在数据库打开和迁移前拒绝启动。

3. 身份同源边界

  • 后端优先比较 /proc/self/ns/pid 与 /proc/1/ns/pid、/proc/self/ns/mnt 与 /proc/1/ns/mnt 的 inode。
  • 普通用户仅因 EACCES/EPERM 无法读取 PID 1 namespace inode 时，要求 PID 1 与后端的 NSpid 链层级一致、PID 1 容器内 PID 为 1，且规范化 mountinfo 视图完全相同；随后使用可读的 self PID namespace inode。任一证据缺失或不一致仍拒绝 confirmed marker。
  • 不得使用 pid: host、宿主 /proc bind mount 或后端兄弟容器。这些方式无法同时通过 NSpid、mountinfo、marker 根 overlay 和数据挂载检查。
  • UID 是权威用户标识；读取进程字段受权限限制时保留可读证据并在 capabilities 返回降级原因。
  • 无需 --privileged，不得为了读取 namespace inode 扩大容器权限。

3.1 数据持久性边界

程序只执行少量高可信度防错：数据目录落在根 overlay，或与 marker 使用同一挂载时拒绝启动；观察到独立挂载时在 status 中返回 persistence_capability=operator_verification_required，而不会自动声称已持久。活动库使用 DELETE journal 并避免在线 vacuum，但运维人员仍需确认权限、配额、文件锁与同步语义，并执行真实容器重建验收。不能仅根据容量或文件系统名称猜测某个 /mnt/* 可用。

3.2 实例进程所有权

dev1/4/5/9 的 PID 文件是权限 0600 的 JSON 状态，不是裸 PID；其中绑定 PID、Linux start ticks、数据目录、marker、端口与本次随机 service token。启动后的状态响应必须携带匹配的 X-Reboot-Trace-Service-Token，避免端口上的旧服务造成假成功。停止前再次核对 start ticks、cmdline 和进程环境；不匹配时拒绝发送 SIGTERM 并保留状态文件。目标 Python 不提供 pidfd，因此以紧邻信号发送的双重身份校验控制 PID 复用窗口。

4. 前端镜像与运行时配置

Vue 在构建阶段生成静态文件，由轻量 Web 服务器提供。当前前端兼容 schema 1～3，应先于 schema v3 后端发布。容器启动时从部署系统挂载的 /usr/share/nginx/html/config/runtime-config.json 加载后端列表，无需重建镜像；升级镜像不得覆盖生产配置。该文件必须设置 Cache-Control: no-store，JS bundle 可使用长期缓存。

{
  "backends": [
    {"id":"dev-1","name":"Maoshanwang_dev_1","baseUrl":"https://dev-1.example/api/v1"},
    {"id":"dev-4","name":"Maoshanwang_dev_4","baseUrl":"https://dev-4.example/api/v1"},
    {"id":"dev-5","name":"Maoshanwang_dev_5","baseUrl":"https://dev-5.example/api/v1"},
    {"id":"dev-9","name":"Maoshanwang_dev_9","baseUrl":"https://dev-9.example/api/v1"}
  ],
  "requestTimeoutMs": 8000,
  "refreshIntervalMs": 5000
}

配置文件是公开静态资源，不包含密钥。baseUrl 直接指向各主机 HTTPS Ingress；前端不做代理，也不携带登录凭证。每个后端的 RT_CORS_ORIGINS 必须包含该前端页面的精确 Origin。

5. Ingress 与跨域合同

  • 每个后端通过独立 HTTPS Ingress hostname 暴露，TLS 证书由 Ingress 管理。
  • 后端应用不做登录鉴权；Ingress/NetworkPolicy/防火墙将服务限制在受控运维网络。不得将无鉴权接口暴露到公共互联网。
  • OPTIONS 预检和 GET 请求必须路由到后端；允许 Origin 来自 RT_CORS_ORIGINS 精确集合，credentials=false。
  • 前端以 credentials: "omit" 请求，不发送 Authorization。Ingress 自身产生的错误可能是 HTML 或非标准 JSON，前端按 HTTP 状态处理。

6. Compose 范围

services:
  frontend:
    image: reboot-trace-frontend:<version>
    volumes:
      - ./runtime-config.json:/usr/share/nginx/html/config/runtime-config.json:ro
    ports:
      - "8088:8080"
    read_only: true
    tmpfs: [/tmp]

Compose 只负责共享前端。后端镜像仅用于构建和依赖门禁，不能部署成目标容器的兄弟容器；生产后端由目标容器内部的进程管理方式启动。

7. 升级、备份和运行

  • 升级镜像前备份数据卷；同一存储格式内的 schema 向前迁移可在事务中执行，但 format v1 到 format v2 必须停服运行显式 storage_repack，服务不会静默重写生产数据。
  • 滚动更新只影响对应主机后端，前端继续展示其他节点并标注该节点短暂离线；容器实例 UUID 与 PID 1 指纹未变化时升级前后属于同一 lifecycle_key，kernel boot ID 不单独决定生命周期。
  • host_id 位于持久卷；重建容器后不变。复制数据卷到另一主机时必须显式重新绑定身份。
  • 前端与后端通过 api_version、schema_version 和 backend_version 协商；前端应提示不兼容后端，而不是静默展示错误数据。
  • 后端自身设置 CPU、内存和日志限制，但资源限额不能低到在主机压力发生时首先被终止；部署时调整 OOM 优先级。

8. 上线检查清单

  • 启动前用 findmnt -T <项目根>/var/reboot-trace（或实际 RT_DATA_DIR）确认独立挂载、权限和配额；项目目录本身不持久时必须改配数据目录。
  • 现有 v3 单库或 format v1 分段布局停服后先运行 storage_repack --dry-run；确认输出策略与线上环境变量一致、within_storage_budget=true，并确认备份目录位于数据目录之外，再执行正式迁移。需要临时覆盖时使用 --storage-limit-mib、--final-snapshots、--trend-snapshots 和 --trend-interval-seconds。
  • 确认 status 返回 persistence_capability=operator_verification_required 及预期 data_path、mountpoint、fs_type；这表示程序完成防错，不表示运维验收完成。
  • 确认身份返回 identity_scope=local_container、namespace_state=supported、marker_storage=container_ephemeral_rootfs。
  • 只重启后端进程：marker、PID 1 指纹和 lifecycle_key 均不变。
  • 持续生成数千次采样：当前生命周期始终不超过 12 个完整快照和 12 个趋势快照，降级进程快照不进入完整计数或最终证据。
  • 写入快照后重建目标容器：marker 与 PID 1 指纹变化，新生命周期为 confirmed；host-id、旧生命周期和对应证据胶囊仍可查询。
  • 强制终止胶囊创建和原子安装过程后重启：manifest 可重建，唯一副本未丢失，活动库和所有可用胶囊通过完整性与外键检查。
  • 以 50 MiB 压测多轮生命周期封存和整胶囊清理，确认长生命周期不会挤掉全部较早重启证据。
