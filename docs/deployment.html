镜像与部署设计

前端、后端分别构建和发布；后端随跳板机部署，前端可独立指向多个后端。

首页需求架构数据库接口前端部署

1. 交付物

backend/Dockerfile
frontend/Dockerfile
deploy/compose.example.yaml
deploy/runtime-config.example.json

两个 Dockerfile 都应支持固定依赖版本、非 root 应用用户、多阶段构建、OCI 标签和健康检查。项目不把 SQLite 文件烘焙进镜像。

2. 后端镜像要求

  • 基于精简 Python 镜像，安装锁定依赖后复制应用代码。
  • 数据目录默认 /var/lib/reboot-trace，必须挂载持久卷；数据库、host_id 和迁移状态位于该卷。
  • 监听 0.0.0.0:8080；健康检查访问 /health/ready。
  • 容器停止信号触发优雅关闭、完成或回滚当前事务并记录 collector_stopped；不得据此终结 boot_id 生命周期或标记主机 clean shutdown。
  • 只读根文件系统，临时文件使用受限 tmpfs；日志输出 stdout/stderr。

关键环境变量

变量默认说明
RT_DATA_DIR/var/lib/reboot-trace持久化目录。
RT_STORAGE_LIMIT_MIB50DB、WAL、SHM 和临时文件的受管预算。
RT_SAMPLE_INTERVAL_SECONDS5采样周期。
RT_PROCESS_TOP_N50各维度排行数量，允许 1～500，避免配置放大采集器开销。
RT_CMDLINE_MAX_BYTES4096脱敏后最大命令长度；可调小，不得超过 4096。
RT_PROC_ROOT/host/proc宿主机 procfs；当前版本的系统与进程指标均由此读取。
RT_HOST_PASSWD/host/etc/passwd可选的宿主机 UID 显示名来源；失败时保留 UID。
RT_CORS_ORIGINS无默认必填的逗号分隔前端精确 Origin；生产禁止 *。

3. 宿主机可见性

普通隔离容器默认只能看到容器自身进程，无法完成跳板机取证。Linux 部署必须显式提供宿主机视图：

  • 使用 host PID namespace（例如 Compose 的 pid: host）。
  • 只读挂载宿主机 /proc；CPU、内存、PSI、进程、mountinfo 和 boot_id 均从配置的 proc root 读取，禁止无声回退到容器自身视图。
  • UID 是权威用户标识。可只读挂载宿主机 /etc/passwd 到单个文件路径用于 best-effort username；不得挂载 shadow，NSS/LDAP 用户无法解析时显示 UID。
  • 磁盘和 inode 只统计后端明确配置或由宿主机 mountinfo 发现并允许的宿主机文件系统，排除 proc、sysfs、tmpfs、overlay 等伪文件系统；响应 capabilities 说明被排除或不可读的范围。
  • 默认丢弃全部 capabilities，再按目标机验证结果增加 SYS_PTRACE 与 DAC_READ_SEARCH，用于读取其他 UID 的受保护 procfs 字段。若安全策略不允许，采集器必须保留可读的 RSS/身份证据，把 I/O 或命令字段置为不可用，不得丢弃整个进程。
  • 不要使用 --privileged。在目标发行版验证 procfs hidepid、SELinux/AppArmor、cgroup v1/v2 与容器运行时限制。

若组织安全策略不允许上述访问，应使用宿主机 systemd 直接运行后端；“提供镜像”不能凌驾于正确的可见性和最小权限。

4. 前端镜像与运行时配置

Vue 在构建阶段生成静态文件，由轻量 Web 服务器提供。容器启动时从部署系统挂载的 /usr/share/nginx/html/config/runtime-config.json 加载后端列表，无需重建镜像；该文件必须设置 Cache-Control: no-store，JS bundle 可使用长期缓存。

{
  "backends": [
    {"id":"dev-01","name":"Maoshanwang_dev_01","baseUrl":"https://dev-01.example/api/v1"},
    {"id":"dev-02","name":"Maoshanwang_dev_02","baseUrl":"https://dev-02.example/api/v1"}
  ],
  "requestTimeoutMs": 8000,
  "refreshIntervalMs": 5000
}

配置文件是公开静态资源，不包含密钥。baseUrl 直接指向各主机 HTTPS Ingress；前端不做代理，也不携带登录凭证。每个后端的 RT_CORS_ORIGINS 必须包含该前端页面的精确 Origin。

5. Ingress 与跨域合同

  • 每个后端通过独立 HTTPS Ingress hostname 暴露，TLS 证书由 Ingress 管理。
  • 后端应用不做登录鉴权；Ingress/NetworkPolicy/防火墙将服务限制在受控运维网络。不得将无鉴权接口暴露到公共互联网。
  • OPTIONS 预检和 GET 请求必须路由到后端；允许 Origin 来自 RT_CORS_ORIGINS 精确集合，credentials=false。
  • 前端以 credentials: "omit" 请求，不发送 Authorization。Ingress 自身产生的错误可能是 HTML 或非标准 JSON，前端按 HTTP 状态处理。

6. Compose 目标形态

services:
  backend:
    image: reboot-trace-backend:<version>
    pid: host
    cap_drop: [ALL]
    cap_add: [SYS_PTRACE, DAC_READ_SEARCH]
    volumes:
      - reboot-trace-data:/var/lib/reboot-trace
      - /proc:/host/proc:ro
      - /etc/passwd:/host/etc/passwd:ro
    environment:
      RT_PROC_ROOT: /host/proc
      RT_HOST_PASSWD: /host/etc/passwd
      RT_STORAGE_LIMIT_MIB: "50"
    restart: unless-stopped

  frontend:
    image: reboot-trace-frontend:<version>
    volumes:
      - ./runtime-config.json:/usr/share/nginx/html/config/runtime-config.json:ro
    ports:
      - "8088:8080"
    read_only: true
    tmpfs: [/tmp]

这是设计示例，不应在未验证目标主机安全配置前直接复制到生产。实际可让所有后端各自在跳板机运行，仅在运维入口部署一个前端。

7. 升级、备份和运行

  • 升级镜像前备份数据卷；启动时自动执行向前兼容迁移，失败必须保持旧数据库可恢复。
  • 滚动更新只影响对应主机后端，前端继续展示其他节点并标注该节点短暂离线；boot_id 未变化时升级前后属于同一生命周期。
  • host_id 位于持久卷；重建容器后不变。复制数据卷到另一主机时必须显式重新绑定身份。
  • 前端与后端通过 api_version、schema_version 和 backend_version 协商；前端应提示不兼容后端，而不是静默展示错误数据。
  • 后端自身设置 CPU、内存和日志限制，但资源限额不能低到在主机压力发生时首先被终止；部署时调整 OOM 优先级。

8. 上线检查清单

  • 验证后端确实看到宿主机 PID 和 boot_id。
  • 模拟服务重启与主机重启，确认生命周期不覆盖。
  • 强制终止写入进程，运行 SQLite integrity check 并验证最后完整快照。
  • 以小预算压测淘汰策略，核对 DB + WAL + SHM 未持续越界。
  • 从前端测试多个 Ingress 后端、单节点超时、允许/拒绝 Origin、Ingress 非 JSON 错误和版本不兼容。
  • 验证浏览器请求不携带 Cookie/Authorization，并确认非受控网络无法访问 Ingress。
  • 用包含 token、password、URI 凭证和超长参数的进程验证数据库、API、事件及日志只出现脱敏且不超过 4096 字节的命令。
