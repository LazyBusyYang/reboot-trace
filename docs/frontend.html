前端功能、交互与样式指南

用于指导 Vue 前端实现多跳板机监控、生命周期浏览和重启前证据分析，确保信息清晰、状态可信且操作一致。

首页需求架构数据库接口前端部署

1. 产品原则

证据优先

默认展示事实、时间和数据完整度，不自动断言重启根因。

生命周期优先

所有历史分析都明确所属主机、lifecycle_key、容器实例、kernel boot ID 和采样时间。

局部故障隔离

一个后端失败不影响其他主机，错误必须落到具体节点。

渐进披露

先显示系统摘要，再按需展开用户、进程以及脱敏且可能截断的命令。

2. 技术基线

  • Vue 3、TypeScript、Vite；使用 Composition API 和 <script setup>。
  • Vue Router 管理页面状态，Pinia 仅保存跨页面共享的后端配置和用户偏好。
  • 请求层按 Ingress 后端实例创建无凭证 client，使用 credentials: "omit"，并统一处理超时、取消、CORS、Ingress 错误和后端错误结构。
  • 图表推荐 ECharts；表格采用支持虚拟滚动、固定列和键盘操作的组件。
  • 时间在网络和状态层保持 Unix 毫秒 UTC，只在展示层转换为用户时区。
  • 前端不得承担权威持久化；Local Storage 只保存筛选条件、主题和列偏好等非敏感信息。
  • API v1 客户端兼容 schema 1～3；发布 schema v3 后端前先升级前端，滚动窗口内必须同时正确展示 v2 与 v3 节点。

3. 信息架构与路由

路由页面核心任务
/多主机总览发现离线、资源压力、采样中断和最近异常生命周期。
/hosts/:backendId主机详情查看当前状态、存储、采集能力和生命周期列表。
/hosts/:backendId/lifecycles/:bootId生命周期详情分析趋势、事件、用户和进程排行。
.../final最终证据聚焦生命周期末尾快照和证据缺口。
.../compare?left=&right=快照对比识别新增、退出和资源增长最快的进程或用户。
/settings前端设置查看已加载后端、时区、刷新周期和显示偏好。

路由必须携带 backendId 与 lifecycle_key；不同后端的数据彼此独立，同一 kernel boot ID 下也可有多个容器生命周期。筛选、时间范围、排序和选中快照应尽量同步到 URL，保证刷新和分享后可恢复。

4. 全局应用框架

┌ 顶栏：产品名 / 全局时间显示 / 刷新状态 / 设置 ┐
├ 侧栏：全部主机、在线状态、主机搜索与分组       ┤
│ ┌ 页面标题 / 主机 / 容器实例 / kernel boot / 数据完整度 ┐ │
│ │ 摘要卡片                                   │ │
│ │ 趋势、排行、事件或对比主内容               │ │
│ └────────────────────────────────────────────┘ │
└ 状态区：后端错误、采样延迟、存储压力提示 ─────┘
  • 桌面端侧栏宽 240～280px，可折叠；移动端改为抽屉。
  • 页面标题下方固定展示面包屑、主机名、生命周期状态和数据时间范围。
  • 全局刷新按钮必须显示“正在刷新”和“最后完成时间”，避免重复触发并发请求。
  • 轮询仅更新当前可见页面；标签页隐藏时暂停高频刷新，恢复时立即刷新一次。

5. 多主机总览

5.1 主机状态卡

每台后端并行请求 /status 和 /latest，显示主机名、连接状态、当前容器实例缩写、kernel boot ID、uptime、最后落盘时间、采样延迟、CPU、可用内存、PSI 和存储使用率。任一请求成功时展示可用部分，不能因另一请求失败清空整张卡。卡片整体可进入主机详情，但卡内按钮必须有独立点击区域。

5.2 排序与筛选

  • 默认优先级：不可达 → 采样严重延迟 → 存储压力 → 高 PSI → 正常。
  • 支持按名称搜索，并按在线状态、生命周期状态和能力筛选。
  • 主机比较必须标明指标时间，时间差超过两个采样周期时不得用颜色暗示精确横向排名。

5.3 并行请求

对所有后端执行独立请求，采用 Promise.allSettled 语义。每张卡拥有自己的 skeleton、成功、空数据、超时、未授权和版本不兼容状态。总览顶部汇总“成功 N / 总数 M”，但不以全屏错误覆盖成功节点。

6. 生命周期详情

6.1 顶部摘要

  • 启动时间、最后观察时间、持续时长、终止状态，以及分列的完整 / 趋势快照数量。
  • 最后成功提交时间及可能的证据缺口；未知值显示“无法确定”，不得显示为 0。
  • 数据保留完整度：final_complete、final_partial、final_minimum 或 summary_only。

6.2 时间轴

  • 默认打开生命周期结束前 10 分钟；活动生命周期默认最近 10 分钟。
  • 图表分组为 CPU/Load、内存/Swap、PSI、I/O、进程与线程；共享十字游标和缩放范围。
  • 在时间轴叠加 OOM、采样延迟、采集错误和保留清理事件标记。
  • 点击任意采样点选择快照，并联动下方用户及进程排行；若降采样无完整快照则明确禁用明细。

6.3 排行区域

CPU、RSS、Swap、读取、写入使用标签页切换，各自维护排序含义。表格至少包含排名、用户、PID、进程名、资源值、线程数、状态和命令摘要。PID 必须与创建时间共同作为前端行键。

7. 最终证据页面

这是取证的默认落点，应减少装饰并提高信息密度：

  1. 顶部说明生命周期终止类型、最终完整快照时间和最后观察时间。
  2. 展示 CPU、可用内存、Swap、Load、三类 PSI、采样漂移等系统证据。
  3. 并列展示各维度 Top 进程与用户汇总，允许在最多 12 个最终完整快照间切换。
  4. 提供“查看前后变化”入口，自动用最终快照与前一个有效快照比较。

页面措辞使用“观察到”“最后记录”“可能存在压力”，禁止使用“导致重启”“根因是”等未经人工确认的结论。

8. 快照对比交互

  • 左右时间点通过时间轴或下拉框选择，默认右侧晚于左侧；交换按钮可互换。
  • 摘要显示系统指标差值，并标注绝对值和百分比；基数为零时不计算百分比。
  • 进程按 pid + create_time_ms 匹配，分为新增、退出、持续和 PID 复用。
  • 默认突出 RSS、Swap、I/O 或 CPU 增幅最大的条目，而不是只看最终绝对排名。
  • 对比请求变更时取消上一次请求，防止较慢响应覆盖较新选择。

9. 通用交互状态

状态表现操作
首次加载保持布局的 skeleton，不用全屏旋转图标。无。
后台刷新保留旧数据，在局部显示刷新标识。允许取消或等待。
空数据说明是无采样、被清理、能力不支持还是筛选无结果。提供清除筛选或返回入口。
超时/离线显示对应后端、上次成功时间和缓存视图的陈旧标记。重试当前节点。
Ingress 401/403视为网络入口策略拒绝，不显示登录入口，也不循环自动重试。提示检查 Ingress 或网络策略。
版本不兼容显示前后端版本和受影响功能。仍允许访问兼容页面。
部分数据黄色数据完整度提示，缺失字段显示短横线。查看能力或保留说明。

10. 视觉规范

10.1 色彩语义

语义建议用途
品牌蓝#315CD6主操作、选中状态、链接。
正常绿#13795B在线、成功；不表示“无风险”。
提醒橙#E59324采样延迟、空间逼近阈值、部分数据。
错误红#C73E4D请求失败、数据不可用、硬阈值。
中性灰#647087未知、未支持、次要信息。

颜色不能是唯一的信息载体，必须配合文本、图标或形状。资源使用率的颜色阈值由后端或配置提供，前端不得散落硬编码。

10.2 排版与间距

  • 基础字号 16px，表格最小 13px；数值使用等宽数字特性。
  • 采用 4px 间距基准；主要卡片内边距 20～24px，卡片间距 16px。
  • 长 lifecycle_key、实例 UUID 和 kernel boot ID 默认显示前 8 位并支持复制完整值；命令行单行省略，详情用可换行等宽文本。

10.3 图表

  • 图例、坐标轴和 tooltip 必须带单位，字节采用 IEC 单位（KiB、MiB、GiB）。
  • 同一指标跨页面保持颜色一致；PSI some/full 使用同色不同明度或线型。
  • 时间缺口必须断线，禁止用插值连接离线时段。
  • 大量序列默认只显示 Top N，用户主动选择后才叠加其他进程。

11. 响应式与无障碍

  • 断点建议：小于 768px 为单栏，768～1199px 为紧凑布局，1200px 以上展开侧栏和多列卡片。
  • 移动端表格切换为关键字段卡片或提供明确横向滚动，不把命令行挤成逐字换行。
  • 所有功能可用键盘完成；可见焦点、语义化标题、表头关联和表单 label 必须保留。
  • 正文与背景对比度至少 4.5:1；图表提供文本摘要或数据表。
  • 尊重 prefers-reduced-motion，轮询更新不触发大面积动画或布局跳动。
  • 动态错误和刷新完成状态使用恰当的 aria-live，避免频繁朗读每次采样。

12. 状态与请求模型

BackendConfig { id, name, baseUrl }
BackendRuntime { status, version, hostId, lastSuccessAt, error }
PageQuery { backendId, bootId, fromMs, toMs, resolution, filters }
AsyncState<T> { state: idle|loading|success|error, data?, error?, stale }
  • 请求缓存键必须包含 backendId、bootId、时间范围、分辨率及所有筛选条件。
  • 路由切换、筛选变化和组件卸载时使用 AbortController 取消请求。
  • 后台刷新可以保留旧数据并标记 stale；切换主机时不得闪现上一主机的数据。
  • 后端返回未知枚举或新增字段时保持前向兼容，并记录可诊断日志。
  • 状态标签严格映射 API：clean_shutdown_observed 显示“观察到正常退出证据”，unclean_or_unknown 显示“未观察到正常收尾或原因未知”；不得缩写成“异常重启”。容器实例与 kernel boot 分栏展示，并显示判定方法和置信度。

13. 性能与安全

  • 生命周期和进程列表始终使用 cursor 分页；单页最多渲染 200 行，继续浏览使用“加载更多”，图表限制点数并请求服务端降采样。
  • 同时请求多个后端时设置并发上限和每节点超时，离线节点使用退避策略。
  • 任何命令行、用户名和服务端消息均按纯文本渲染，禁止使用未经净化的 v-html。
  • 运行时配置是公开资源，不包含 Token。请求不得携带 Authorization 或 Cookie；所有后端 baseUrl 必须使用 HTTPS Ingress 地址。
  • 命令行只按纯文本显示 cmdline_redacted；当 truncated 或 redaction_status 为 failed_closed 时给出明确提示，不提供查看原文操作。
  • 页面卸载时清理定时器、图表实例和事件监听，避免长期值守页面内存增长。

14. 组件建议

组件职责

AsyncBoundary统一加载、空、错误、部分成功和重试交互。

15. 测试与验收

  • 单元测试覆盖单位格式化、时间转换、证据缺口、枚举回退和进程身份匹配。
  • 组件测试覆盖 loading、empty、partial、error、stale 和权限状态。
  • 端到端测试至少包含两个成功后端、一个离线后端、生命周期切换和快照对比。
  • 验证深链接刷新、浏览器前进后退和 URL 筛选恢复。
  • 用大数据集验证表格与图表性能，用窄屏和键盘完成核心取证流程。
  • 验收时确认 UI 不会把 unknown 展示为 clean，也不会把高资源占用表述为已确认根因。
